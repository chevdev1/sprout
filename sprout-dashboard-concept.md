# Sprout — Личный кабинет (Dashboard)
### Визуальная концепция, архитектура Web3-авторизации и roadmap
**Статус:** черновик на утверждение · подготовлено на основе актуального деплоя [sprout-two-alpha.vercel.app](https://sprout-two-alpha.vercel.app/#top)

## 0. Важная оговорка по стеку

Лендинг сейчас — статический HTML/CSS/vanilla JS без сборки, задеплоенный напрямую на Vercel (никакого React/Next/бандлера нет вообще). Бриф просит React + Tailwind + Wagmi/RainbowKit — это значит, что ЛК технически будет **отдельным приложением**, не продолжением текущих файлов. Рекомендация ниже (раздел 5) — завести ЛК на **Next.js (App Router)**, а не на чистом Vite-React, ровно по одной причине: SIWE требует backend-эндпоинты для выдачи nonce и верификации подписи, а Next.js даёт их «бесплатно» через Route Handlers на том же Vercel-деплое, без отдельного сервера. Это архитектурное решение нужно подтвердить явно — оно определяет весь Roadmap ниже.

## 2. Web3-авторизация: архитектура (SIWE)

### 2.1 Почему SIWE, а не "просто подключить кошелёк"
Подключение кошелька (`eth_requestAccounts`) само по себе **не является аутентификацией** — это просто раскрытие адреса, его может запросить любой сайт без согласия пользователя что-либо подтверждать. Аутентификация требует **подписи сообщения** (доказательство владения приватным ключом) — это и есть EIP-4361 / Sign-In with Ethereum.

### 2.2 Флоу (production-grade)

```
Клиент                          Backend (Next.js Route Handlers)
  │                                       │
  │  GET /api/auth/nonce                  │
  │ ─────────────────────────────────────>│  генерирует crypto-случайный nonce,
  │                                       │  кладёт в серверный store (Redis/DB)
  │  <───────────────────────────────────  с TTL (~5-10 мин), привязывает к
  │        { nonce }                      │  анонимной cookie-сессии
  │                                       │
  │  формирует SiweMessage:               │
  │  domain, address, statement,          │
  │  uri, version=1, chainId, nonce,      │
  │  issuedAt, expirationTime             │
  │                                       │
  │  wallet.signMessage(message)          │
  │  (RainbowKit/wagmi useSignMessage)    │
  │                                       │
  │  POST /api/auth/verify                │
  │  { message, signature }               │
  │ ─────────────────────────────────────>│  1. SiweMessage.verify({signature})
  │                                       │  2. nonce совпадает и не использован
  │                                       │  3. domain === наш домен (anti-phishing)
  │                                       │  4. expirationTime не истёк
  │                                       │  5. chainId ∈ allowlist (Robinhood Chain)
  │                                       │  6. если address — смарт-контракт
  │                                       │     (Safe и т.п.) → EIP-1271 on-chain
  │                                       │     проверка вместо ecrecover
  │                                       │  → nonce инвалидируется (одноразовый)
  │  <───────────────────────────────────  → выпускается сессия
  │   Set-Cookie: session (httpOnly,      │
  │   Secure, SameSite=Lax, signed JWT    │
  │   или opaque id → серверный store)    │
```

### 2.3 Обязательные требования безопасности
- **Nonce — только на сервере.** Никогда не доверять nonce, пришедшему от клиента без сверки с серверным store. Одноразовый, короткий TTL.
- **Сессионный токен — httpOnly cookie, не localStorage.** JWT/токен в localStorage читается любым инжектированным JS (XSS) — для продукта с реальными деньгами это неприемлемо.
- **Проверка domain и chainId внутри подписанного сообщения** — защита от фишинга (подпись, полученная на поддельном домене, не пройдёт проверку на нашем) и от replay с другой сети.
- **Rate limiting** на `/api/auth/nonce` и `/api/auth/verify` (защита от брутфорса/спама).
- **Ре-аутентификация при смене адреса или сети** в кошельке — сессия должна инвалидироваться, если `wagmi`'s `useAccount` фиксирует смену адреса относительно того, что был в подписанном сообщении.
- **CSRF** — при cookie-based сессии обязательна SameSite=Lax/Strict + проверка Origin/Referer на state-changing запросах (заказ карты, заморозка, пополнение).

### 2.4 Рекомендуемый стек реализации
- `wagmi` + `viem` + `RainbowKit` — подключение кошелька, мультичейн, UI коннектора (уже в требованиях).
- `siwe` (официальный npm-пакет от Spruce/Sign-In with Ethereum) — построение и верификация сообщения на сервере, не писать вручную.
- Сессии: `iron-session` или собственный signed-cookie слой поверх Next.js Route Handlers — не хранить сессию в самом JWT-теле без server-side возможности отозвать (нужен revocation list или короткий TTL + refresh).
- Существующий готовый пример под этот стек — `@rainbow-me/rainbowkit-siwe-next-auth` (RainbowKit + NextAuth CredentialsProvider), можно взять как основу вместо написания auth-слоя с нуля.

## 3. Визуальная концепция ЛК

Общий принцип: тёмная тема по умолчанию (`--ink` фон), glassmorphism-панели, bento grid для дашборда, карта — центральный "hero"-объект интерфейса (визуально она должна читаться так же дорого, как 3D-росток на лендинге).

### 3.1 Header
- Слева: логотип Sprout (тот же знак-лист, `--sprout` на `--ink`).
- По центру/справа: **Network badge** (Robinhood Chain, с точкой-индикатором как у `.eyebrow .dot` на лендинге), **Balance** (агрегированный баланс карты, крупным моноширинным числом — паттерн уже есть в `.grow-amount`), **Wallet chip** (сокращённый адрес `0x4a...9F2`, аватар/blockie, при клике — dropdown: Copy address / Change wallet / Disconnect).
- Тот же liquid-glass эффект хедера, что и на лендинге (`backdrop-filter: blur(20px) saturate(150%)`, inset-хайлайт сверху), но постоянно в "scrolled"-состоянии (плотнее), так как в ЛК нет длинного скролла-реветара.

### 3.2 Sidebar / Навигация
Вертикальный сайдбар (десктоп) / нижний таб-бар или выезжающее меню (мобайл — переиспользовать паттерн уже существующего `.dock`, quick-nav дока с лендинга, он у нас уже спроектирован и обкатан):
- **Overview** (главный дашборд)
- **Card** (управление картой — ключевой раздел)
- **Grow-back** (аналог калькулятора с лендинга, но с реальными данными: история контрибуций, текущий тикер, график)
- **Activity** (лента транзакций)
- **Settings** (профиль)

Активный пункт подсвечивается `--sprout` — паттерн 1:1 с тем, как уже подсвечивается активный шаг в секции "How it works" на лендинге (`.step-card.is-active`).

### 3.3 Main Dashboard — Bento grid
Сетка виджетов (переиспользуем `.feature-grid`-подобный bento-паттерн с лендинга, hairline-границы между ячейками, одна ячейка — `highlight`/тёмная):

| Виджет | Содержание |
|---|---|
| **Balance** (крупная ячейка) | Общий баланс карты в USD-эквиваленте + разбивка по активам (ETH/USDG/акции), кнопки Top up / Freeze прямо на виджете |
| **Grow-back** (`highlight`, акцентная тёмная ячейка — как "Unique to Sprout" на лендинге) | Текущий тикер, накоплено за месяц/всего, мини-график, CTA "Change ticker" |
| **This month spend** | Сумма трат, % к прошлому месяцу |
| **Recent activity** | 3-5 последних транзакций (переиспользуем визуальный паттерн `.grow-feed .item` с hero-демо лендинга — слайд-ин строк с плюсующимися суммами) |
| **Network status** | Robinhood Chain, статус подтверждения последней транзакции |

### 3.4 Блок виртуальной карты Sprout (ключевой раздел)

#### A. Флоу заказа карты (для пользователя без карты)
Пошаговый онбординг, каждый шаг = отдельный экран с прогресс-индикатором (переиспользуем визуальный язык `.how-rail`/прогресс-полосы с лендинга):

1. **Connect wallet** (если ещё не подключен / SIWE ещё не пройден) — см. раздел 2.
2. **Choose card type** — Virtual (Free, instant) сразу активна; Physical (At cost — точная сумма подтягивается с backend/issuer API, а не хардкодится, т.к. на лендинге прямо сказано "shown before order") с пометкой "ships after virtual card is active" (это дословная логика с лендинга, FAQ №9).
3. **Fund your card** — выбор актива для фандинга (ETH / USDG / tokenized stocks), сумма, подтверждение транзакции через подключённый кошелёк (on-chain перевод на кастодиальный/смарт-контрактный адрес карты).
4. **Set your grow-back ticker** — тот же UI-паттерн, что и `.calc-ticker-choice` на лендинге (кнопки-пилюли AAPL/ETH/SPY/NVDA и т.п.), плюс слайдер rate 0.5%–5% (переиспользуем `.calc-panel` 1:1 по стилю).
5. **Review & confirm** — сводка: card type, funding asset, grow-back ticker+rate, applicable fees (issuance Free / spend 1.0% / no monthly fee) — прямо цитирует таблицу тарифов с лендинга, чтобы пользователь видел те же цифры, что видел на маркетинговой странице (доверие/консистентность).
6. **Card issued** — success-экран с "прилетающей" картой (анимация в духе card-tap с лендинга: 3D pop + зелёный glow), сразу показывает виртуальную карту готовой к использованию (Apple Pay/Google Pay provisioning — кнопка "Add to Wallet").

Копирайт на всех шагах явно помечать статус пре-запуска там, где уместно (по аналогии с hero-note на лендинге: *"Availability and card terms are set at launch"*) — особенно для физической карты и ATM-снятия, где итоговые условия ещё не финальны.

#### B. Управление выпущенной картой
- **Визуальный концепт карты** — 1:1 переиспользование `.mini-card`/`.pay-card` с лендинга: тёмный градиент `--ink → --ink-2`, лого + "Robinhood Chain" бейдж сверху, замаскированный номер, "ETH · USDG · STOCKS" снизу. В ЛК добавляем glass-обводку (`border:1px solid rgba(255,255,255,.1)`) и лёгкую idle-левитацию (та же техника, что у 3D-ростка — `translateY` осцилляция на `requestAnimationFrame`, не бесплатный CSS keyframe с "швом").
- **Front/back флип** — по клику показываем CVV/полный номер (после доп. подтверждения — biometric/PIN/повторная подпись).
- **Balance** — крупно, с тем же "цифры плюсуются" паттерном, что в hero-демо лендинга (`grow-amount.is-updated` pop-анимация).
- **Top up** — модалка: выбор актива из подключённого кошелька → сумма → подпись транзакции (wagmi `useSendTransaction`/контрактный вызов) → progress/confirmation state (pending → confirmed, с учётом времени сети).
- **Freeze/unfreeze** — один тоггл, мгновенный визуальный фидбэк (карта "замораживается" визуально — desaturate + мороз-иконка, реализуемо как CSS-фильтр transition).
- **Grow-back settings inline** — изменить тикер/rate прямо с экрана карты, без ухода на отдельную страницу.

### 3.4.C Реализовано в проде (2026-09) — платный выпуск карты + кастомизация за кэшбек

Флоу заказа карты из 3.4.A частично реализован и живёт на `sprout-two-alpha.vercel.app/app`, с одним осознанным отличием от изначального черновика: выпуск карты **платный ($5, разовый платёж)**, а не Free — доступ к кабинету открывается только после оплаты. Актуальная последовательность:

1. **`/apply`** — экран оплаты: фи $5, страна выпуска "Europe (any)", тип карты Virtual/instant, кнопка Connect wallet (RainbowKit) и кнопка "Pay $5 & get card". До оплаты весь остальной кабинет закрыт (гейт по стадии `unpaid → paid → onboarded`, см. `src/components/CardAccessGate.tsx`) — прямой заход на `/`, `/card`, `/settings` и т.д. редиректит обратно на `/apply`.
2. **`/welcome`** — короткий полноэкранный "Welcome to Sprout" (пульсирующая анимация + звуковой чайм, синтезированный через Web Audio API, без внешнего аудиофайла), автопереход через 2.2с.
3. **`/onboarding`** — визард из 4 шагов, это и есть **"клиент настраивает карту за кэшбек"**:
   - Шаг 1 — тип карты (Virtual, $5 one-time) + выбор актива для фандинга (ETH / USDG / Tokenized stocks).
   - Шаг 2 — выбор **grow-back тикера** (AAPL / ETH / SPY ETF / NVDA / Other RWA) — это и есть настройка кэшбека: клиент сам выбирает, во что уходит доля с каждой покупки.
   - Шаг 3 — Review: сводка выбора + таблица комиссий с лендинга (issuance теперь показан как "$5.00 · Paid ✓").
   - Шаг 4 — полноэкранный "Card issued" момент (второй welcome-чайм), переход в кабинет.
   Выбранный на шаге 2 тикер сохраняется (`saveCardSetup()`, `src/lib/cardAccess.ts`) и реально отображается в Overview/Card как `rewards.ticker` — не захардкожен.
4. **После онбординга** — баланс/активность на Overview и Card **честно нулевые** (свежевыпущенная карта ничем не профинансирована по-настоящему в Phase 1 — визард только выбирает *намерение*, не двигает реальные деньги), с соответствующими empty-state копирайтами ("No funds yet — top up to start spending", "No transactions yet"). Единственное реальное поле, перенесённое из онбординга — выбранный grow-back тикер.

Всё это — **frontend-only мок** (localStorage вместо реальной сессии/платежа), соответствует границам Фазы 3 из раздела 4 ниже. `/reset` (`src/app/reset/page.tsx`) отключает кошелёк и чистит весь связанный localStorage (наш + wagmi/RainbowKit/WalletConnect) для повторного прохождения флоу при тестировании.

### 3.5 Настройки профиля
- Подключенные кошельки (мульти-wallet, primary/secondary), возможность добавить ещё один и подписать с него (linking flow — отдельная SIWE-подпись, привязка к тому же аккаунту).
- Уведомления (email — тот же `hello@sprout.cash`-паттерн, но реальная форма, не mailto).
- Security: активные сессии (список устройств/IP с возможностью revoke — это прямое следствие серверных сессий из раздела 2), disconnect all.
- Legal/Docs — прямая ссылка на уже существующий `docs.html` (не дублировать контент, уже есть подробный fee breakdown и security-раздел).

**Реализовано (2026-09):** `/settings` (`src/app/settings/page.tsx`) — подключенный кошелёк (реальный адрес из wagmi `useAccount`, кнопка "Connect another wallet" открывает RainbowKit-модалку), уведомления (3 тоггла, локальный UI-стейт), активные сессии (пока статичный мок — реальный список требует серверных сессий из раздела 2, ещё не реализованных). Multi-wallet linking и Legal/Docs-ссылка — ещё не сделаны.

## 4. Roadmap разработки

### Фаза 1 — Сетап окружения, UI-кит, Web3-провайдеры
- Инициализация Next.js (App Router) проекта — новый репозиторий/поддиректория, отдельная от текущего статического `site/`.
- Tailwind config: перенос токенов лендинга (цвета, radius, motion-durations/easing) как есть — не изобретать новую систему.
- Базовый UI-кит: Button/Card/Modal/Input по мотивам уже существующих CSS-классов лендинга (`.btn-primary`, `.feature-card`, glass-панели).
- `wagmi` + `viem` + `RainbowKit` провайдеры, конфиг сети (Robinhood Chain RPC/chainId).
- Деплой skeleton-страницы на Vercel (отдельный проект/поддомен, например `app.sprout.cash` или `sprout-dashboard.vercel.app` на старте).

### Фаза 2 — SIWE-авторизация и API
- Route Handlers: `/api/auth/nonce`, `/api/auth/verify`, `/api/auth/logout`.
- Серверное хранилище сессий/nonce (Redis — Vercel KV подходит нативно).
- Middleware защиты приватных роутов (`/dashboard/*`) — редирект на Connect Wallet при отсутствии валидной сессии.
- Юнит/интеграционные тесты на верификацию подписи, включая невалидные/просроченные/replay-кейсы.

### Фаза 3 — Вёрстка дашборда и флоу заказа карты (фронтенд, без реальных данных)
- Header, Sidebar/dock, bento-grid Overview на моках.
- Полный флоу заказа карты (шаги 1-6 из раздела 3.4.A) как frontend-состояния, без реального backend issuer-интеграции — данные тарифов уже статичны и совпадают с лендингом.
- Экран управления картой (визуал + фейковые данные), включая flip/freeze/top-up UI без реальных транзакций.

### Фаза 4 — Реальные данные, управление картой, полировка
- Интеграция с card-issuer API (реальный заказ/выпуск карты) — зависит от выбранного партнёра-эмитента, отдельная задача вне фронтенда.
- Реальные on-chain транзакции для top-up (wagmi `useSendTransaction`/контракт), баланс с реального адреса/индексатора.
- Freeze/unfreeze с реальным статусом карты.
- Полировка анимаций строго на токенах лендинга (`--ease-out-expo`, `--motion-*`), проверка `prefers-reduced-motion` везде по аналогии с лендингом.
- Переключение трёх CTA на лендинге (`Get early access` / `Get your card` / `Request early access`) на реальный `/dashboard` роут.
